# Deploy — feature/user-access-password (2026-08-26)

Cobre os três épicos da branch: acesso de usuários (roles + primeiro acesso/recuperação),
experiência do parceiro e documento do cliente.

**Ordem obrigatória: SQL → backend → frontend** (o código novo depende do schema novo;
o código antigo funciona com o schema novo).

## 0. Pré-requisito

Merge das branches `feature/user-access-password` nos DOIS repos (backend e
cash-by-card-front). Se o deploy do backend é disparado por push na main (workflow SSH),
rode o SQL ANTES do merge/subida para não restartar o serviço sem schema.

## 1. Banco de dados (SQL manual, na ordem)

```sql
-- 1) Acesso de usuários (password nullable + tabela de tokens)
SOURCE db/migrations/2026-08-24-user-access-password.sql;

-- 2) BOOTSTRAP OBRIGATÓRIO — ninguém cria 'organization' pela API:
UPDATE user SET role='organization' WHERE email='<email-do-dono>';

-- 3) Documento do cliente
SOURCE db/migrations/2026-08-26-client-document.sql;
```

Usuários `admin` existentes continuam válidos no role admin.

## 2. Backend no servidor

### 2.1 Variáveis novas no `.env` de produção

```bash
# link dos emails de reset (URL REAL do frontend em produção)
FRONT_URL=https://seu-frontend.com

# pasta dos documentos dos clientes — VOLUME (nunca dentro do código)
DOCS_DIR=/var/cashbycard/docs

# SMTP real (sem isso, os links de senha caem no console do servidor e ninguém vê)
SMTP_HOST=smtp.seuprovedor.com
SMTP_PORT=587          # 587/STARTTLS — 465 NÃO é suportado
SMTP_USER=...
SMTP_PASSWORD=...
SMTP_FROM=noreply@seudominio.com
```

`JWT_SECRET_KEY` já deve existir (login atual usa).

### 2.2 Pasta de documentos

```bash
mkdir -p /var/cashbycard/docs
chown <usuário-do-serviço> /var/cashbycard/docs
```

### 2.3 Restart do serviço backend

## 3. Frontend

Pull + `npm run build` (ou redeploy Vercel/CI). Conferir `.env.production`:
`VITE_API_BASE_URL` apontando para a URL de produção da API. Nenhuma env nova.

## 4. Fumaça pós-deploy (5 min)

- [ ] Login com o dono (organization) → nav com **usuários** e **alterar senha**
- [ ] `/usuarios` → criar partner → **email chega** → link abre primeiro acesso → senha
      forte (ex.: `Teste@123`) → login com ela
- [ ] Como partner: home = relatório dele; `/cliente` só os dele (sem excluir);
      simulações carregam maquininhas
- [ ] Como admin: em `/usuarios` vê **apenas parceiros**
- [ ] Cliente: subir PDF → Ver → trocar por JPEG (substitui) → Remover
- [ ] "Esqueci minha senha" com email real → email com link
- [ ] Logout (sidebar → "Sair da conta" → confirmar)

## Armadilhas

- **SMTP vazio = fluxo de senha morto em produção** (links só no console) — item mais
  fácil de esquecer
- Sem o `UPDATE ... role='organization'`, ninguém gerencia usuários no primeiro dia
- Backup do servidor agora tem 2 itens: dump MySQL **+** pasta `DOCS_DIR`
- Trocar a senha do dono no deploy (opcional):
  `UPDATE user SET password=MD5('<nova>') WHERE email='<dono>';` (MD5 é o padrão atual;
  migração para bcrypt está no backlog)
- Débitos conhecidos que NÃO bloqueiam: MD5, rate limit no forgot-password,
  role-gate no `/public/*`, `Limit(100)` em finders
